# 计划：UI 框架迁移（Slint → Iced 0.14）

日期：2026-08-12
分支：`feat/iced-ui`
状态：已完成

## 背景与动机

1. **段落编辑器是 Slint 的痛点**：Slint 的 `TextInput` 在嵌套布局下
   行高不随换行自适应，原实现被迫「每段一个 TextInput」并堆叠
   `est_lines` 行高估算、`scroll_to_row` 手算滚动、`focus-nonce` 聚焦令牌、
   右对齐末尾空格占位等 workaround（`main_window.slint` / `main.rs`）。
   用户诉求是「一个真正的多行文本框」（对齐 Python 版 QTextEdit）。
2. **许可**：crates.io 版 Slint 为 GPLv3，程序整体受 GPL 传染；
   Iced 为 MIT，可恢复纯 MIT 分发。
3. gpui 评估结论（2026-08）：crates.io 的 gpui 0.2.2 是「裸框架」，
   无 Button/Checkbox/Input/Slider/ComboBox 等控件（官方 ui crate 在
   GPL 的 Zed 仓库且不可独立编译），控件与多行编辑器需全部自研；
   Iced 0.14 自带 TextEditor（多行）+ 全套控件 + tiny-skia 软件渲染，
   迁移成本最低。

## 方案

- 框架：`iced = 0.14`，features：`tiny-skia`（纯 CPU 软件渲染，保留
  「无 GPU 老机器/虚拟机可跑」目标）、`image`、`advanced-shaping`
  （cosmic-text 整形 + 系统字体回退，中文正常显示）、`tokio`、`tester`
- 段落编辑器：**单个多行 TextEditor + 平行段落格式数组**（`ParaFormat`），
  `\n` 即分段，`Content::cursor().position.line` 即光标所在段，
  对齐/缩进按钮作用于光标段，段增删时格式数组自动同步
  （`src/ui/editor.rs`）
- 参数层：`UiParams` 纯数据载体 + `collect_params` / `apply_preset`
  纯函数（`src/ui/params.rs`），替代 Slint 控件绑定与 `main.rs` 收集逻辑
- 业务调度：`HandwriteApp`（状态 / Message / update / subscription），
  防抖自动预览（停止输入 300ms，`iced::time::every` 轮询），
  渲染/导出/文件对话框走 `tokio::task::spawn_blocking` 后台线程
- core/ 引擎零改动

## 与 Slint 版的行为差异

- 文本/参数变化都会触发防抖自动渲染（README 承诺的「停止输入 300ms 后
  自动渲染」，Slint 版实际只在格式按钮/预览按钮时触发）
- 渲染任务串行执行（渲染期间的新改动在完成后立即再渲染），
  无需 Slint 版的渲染代次守卫

## 编辑器可视化对齐（2026-08 迭代）

cosmic-text 0.15（iced 0.14 底层）不支持 buffer 级对齐（0.19 已支持，
待 iced 升级），因此段落编辑器改为**每段一个 TextEditor**：

- 每段独立 `Content` + 段格式（对齐/缩进），段格式直接作用于布局：
  居中/右对齐段按估算文本宽度收缩 + 容器水平对齐，**编辑器内可视化对齐**
- 缩进 = 段前留白（宽度 = 缩进字符数 × 字号）
- key_binding：回车分段（光标处拆段、后半段继承格式）、段首退格并入上一段
- 粘贴多行自动拆段（新段继承格式）；程序化聚焦用 `widget::operation::focus`
- 超长居中/右对齐段回退占满宽度（wrap 换行，对齐以预览为准）

已知限制（iced 0.14）：`Content::move_to` 把字符列当字节索引，
非 ASCII 文本程序化移动光标会触发 cosmic-text 断言（运行时不受影响，
用户操作的光标由 cosmic-text 管理；已在上游跟进）。
